# SkinCode — описание frontend-прототипа

## 1. О проекте

SkinCode — сервис подбора оттенков тональных средств без фотографии и сканирования лица. Пользователь указывает тональное средство и оттенок, которые ему уже подходят, после чего приложение предлагает похожие оттенки других продуктов и объясняет рекомендации.

Цель текущей версии — проверить сам формат продукта, пользовательский сценарий и визуальную подачу. Это интерактивный frontend-прототип с демонстрационными данными, а не готовая система точного подбора оттенков.

## 2. Формат запуска

Приложение должно работать как Telegram Mini App — web-приложение, открываемое внутри Telegram-бота. При этом интерфейс должен нормально запускаться и в обычном мобильном браузере для локальной разработки и демонстрации.

На текущем этапе backend не нужен. Необходимо реализовать только клиентскую часть:

- без сервера и базы данных;
- без настоящей регистрации и авторизации;
- без реального ML-алгоритма;
- без подключения каталогов магазинов;
- без реальных цен и остатков;
- без оплаты внутри приложения;
- без отправки данных в Telegram-бота.

Товары, совпадения, магазины, цены и статусы наличия берутся из локальных mock-данных. Выбор пользователя и сохранённые позиции можно хранить в `localStorage`. После перезагрузки страницы введённые данные желательно восстанавливать.

Telegram Web App SDK подключается только на уровне оболочки: инициализация приложения, `ready`, `expand`, safe-area и корректная работа кнопки «Назад». Если приложение открыто вне Telegram, эти вызовы должны безопасно игнорироваться.

## 3. Основная гипотеза

Пользователю проще подобрать новый тональный продукт по знакомому оттенку, чем определять цвет кожи по фотографии или самостоятельно выбирать подтон.

Главное сообщение продукта:

> Твой тон. В новом флаконе. Подбор по тональному средству, которое тебе подходит. Без фото.

## 4. Основной пользовательский сценарий

```text
Главная
  → выбор знакомого продукта
  → выбор оттенка
  → оценка того, насколько хорошо он подходит
  → необязательные предпочтения
  → список рекомендаций
  → карточка рекомендованного продукта
  → список магазинов
  → демонстрационный переход во внешний магазин
```

Подбор состоит из трёх логических шагов:

1. Знакомое средство и его оттенок.
2. Оценка оттенка и, при желании, добавление второго или третьего эталона.
3. Необязательные предпочтения по типу кожи, финишу и бюджету.

Экран результатов не считается шагом ввода.

## 5. Экраны

### 5.1. Главная

- логотип SkinCode;
- заголовок и короткое объяснение механики;
- крупная предметная композиция с тональным средством;
- основная кнопка «Подобрать оттенок»;
- ссылка «Как это работает»;
- нижняя навигация: «Главная», «Подбор», «Мои тона».

### 5.2. Поиск знакомого средства

- поле поиска по бренду и названию;
- список популярных средств до ввода запроса;
- фильтрация mock-каталога по введённому тексту;
- обработка пустого результата;
- действие «Нет моего средства»;
- выбранный продукт визуально выделяется.

### 5.3. Выбор оттенка

- карточка выбранного продукта;
- поиск по коду оттенка;
- сетка доступных оттенков;
- выбранный оттенок выделяется обводкой;
- подсказка: «Выбирай номер на флаконе, а не цвет на экране».

Цветные кружки служат только иллюстрацией. Нельзя создавать впечатление, что оттенок определяется по цветопередаче экрана.

### 5.4. Оценка эталонного оттенка

Вопрос: «Как он тебе подходит?»

Варианты:

- идеально;
- светлее кожи;
- темнее кожи;
- желтит;
- розовит.

«Идеально», «светлее» и «темнее» — взаимоисключающие ответы. Цветовой сдвиг можно выбирать отдельно. Пользователь может добавить ещё одно средство, но это необязательно.

### 5.5. Предпочтения

Экран можно пропустить. Он влияет на подбор формулы, но не должен подменять сравнение оттенков.

- тип кожи: сухая, жирная, комбинированная, не знаю;
- финиш: матовый, естественный, сияющий;
- бюджет: любой, до 3 000 ₽, до 5 000 ₽.

### 5.6. Результаты

- эталонный продукт пользователя;
- фильтры «Все», «В наличии», «До 3 000 ₽»;
- карточки рекомендованных средств;
- бренд, линейка, оттенок, цена и статус наличия;
- краткое объяснение: близость оттенка и особенности формулы;
- кнопка сохранения;
- переход в карточку продукта.

В прототипе нельзя использовать заявления вроде «совпадение 98%», пока нет реального откалиброванного алгоритма. Допустимые формулировки: «Близкий оттенок», «Предварительный вариант», «Мало данных».

### 5.7. Карточка рекомендации

- крупное изображение продукта;
- бренд, название и код оттенка;
- блок «Почему этот вариант»;
- визуальное сравнение эталонного и нового оттенка;
- напоминание проверить средство при дневном свете;
- кнопки «Где купить» и «Сохранить».

### 5.8. Где купить

- выбранный продукт и оттенок;
- список демонстрационных магазинов;
- цена и наличие;
- кнопка «Перейти»;
- пояснение, что откроется страница выбранного оттенка в магазине.

Для прототипа внешние ссылки могут быть заглушками. Нажатие должно показывать понятное уведомление, а не вести на случайную главную страницу магазина.

### 5.9. Мои тона

- основной эталон пользователя;
- добавленные средства;
- отдельный сезонный вариант, например оттенок для загара;
- сохранённые рекомендации;
- запуск нового подбора.

### 5.10. Сохранённая подборка

- сохранённые продукты;
- указание эталона, на основе которого они подобраны;
- удаление из сохранённого;
- демонстрационная кнопка «Поделиться ссылкой»;
- сохранение без обязательной регистрации.

### 5.11. Обратная связь

После условного использования средства пользователь может ответить:

- ещё не пробовала / уже попробовала;
- подошёл / светлее / темнее / желтит / розовит;
- формула понравилась / не подошла.

В текущем прототипе ответ сохраняется локально.

### 5.12. Недостаточно данных

Если для пары продуктов нет mock-соответствия, приложение не должно придумывать рекомендацию. Нужно показать экран:

- «Пока мало данных»;
- «Добавить другой эталон»;
- «Проверить название средства»;
- «Отправить название» для отсутствующего продукта.

## 6. Логика демонстрационного подбора

Для тестовой версии достаточно детерминированных соответствий в локальном JSON или TypeScript-файле.

Пример структуры:

```ts
type Product = {
  id: string;
  brand: string;
  name: string;
  image: string;
  finish: "matte" | "natural" | "radiant";
  skinTypes: Array<"dry" | "oily" | "combination" | "normal">;
  shades: Array<{
    id: string;
    code: string;
    swatch: string;
  }>;
};

type DemoMatch = {
  sourceShadeId: string;
  targetShadeId: string;
  level: "close" | "possible";
  explanation: string;
};
```

Подбор может работать так:

1. Найти заранее заданные `DemoMatch` для выбранного оттенка.
2. Отфильтровать их по бюджету и наличию.
3. Повысить в выдаче продукты, соответствующие выбранному финишу и типу кожи.
4. Если соответствий нет, открыть экран «Пока мало данных».

Введённый пользователем продукт не должен появляться среди рекомендаций как новый вариант.

## 7. Визуальное направление

Основная палитра — белая и холодная светло-серая. Бежевый используется только внутри жидкости тонального средства и небольших свотчей.

- белый и серебристо-серый фон;
- полупрозрачные карточки из матового стекла;
- тонкие светлые границы;
- мягкие нейтральные тени;
- прозрачные стеклянные формы и преломления на фоне;
- чёрные основные кнопки;
- крупные предметные изображения флаконов;
- высокий контраст текста;
- минимум декоративных элементов внутри форм.

Размытие применяется к фону стеклянной поверхности, но не к тексту. Текст и элементы управления должны оставаться чёткими.

Типографика единая на всех экранах: современный гротеск в духе Inter или SF Pro. Заголовки жирные, основной текст обычного начертания. Не использовать шрифты с засечками и рукописные подписи. Логотип `SKINCODE` — простой uppercase wordmark тем же визуальным языком.

Референсные изображения и подробный UX-план находятся в папке `outputs/skincode-ui-concept`.

## 8. Анимации

- нажатие кнопки: лёгкое уменьшение до `0.98`, около 120 мс;
- переход между шагами: прозрачность и небольшое горизонтальное смещение, около 220 мс;
- появление добавленного эталона: около 180 мс;
- сохранение: короткая анимация заполнения иконки закладки;
- загрузка рекомендаций: короткое состояние «Сопоставляем оттенки» без искусственной долгой задержки;
- учитывать `prefers-reduced-motion`.

## 9. Адаптивность и Telegram

Основной сценарий mobile-first, ориентир по ширине — 390 px. Интерфейс должен корректно работать примерно от 320 до 480 px и учитывать safe-area Telegram WebView.

На desktop приложение можно показывать в центральной мобильной колонке с аккуратным фоном. Полноценный desktop-интерфейс для этой тестовой версии не обязателен.

Нужно предусмотреть:

- `100dvh` вместо жёсткого `100vh`;
- отступы `env(safe-area-inset-top)` и `env(safe-area-inset-bottom)`;
- отсутствие горизонтального скролла;
- кликабельные зоны не меньше 44 × 44 px;
- корректное поведение системной кнопки «Назад»;
- сохранение состояния при переходах между экранами.

## 10. Рекомендуемый стек

Если проект создаётся с нуля:

- React;
- TypeScript;
- Vite;
- React Router;
- Tailwind CSS или CSS Modules;
- Framer Motion для небольших переходов;
- Lucide для интерфейсных иконок;
- Telegram Web App SDK через небольшой отдельный адаптер;
- `localStorage` для состояния тестового пользователя.

Компоненты и бизнес-логику следует отделить от mock-данных, чтобы позднее заменить локальные файлы настоящим API без переписывания интерфейса.

## 12. Состояния интерфейса

Нужно предусмотреть:

- обычное состояние;
- выбранный элемент;
- disabled-состояние кнопки;
- пустой поиск;
- отсутствие рекомендации;
- загрузку;
- локальную ошибку;
- успешное сохранение;
- восстановление сохранённого состояния.

При возврате на предыдущий экран выбор пользователя не сбрасывается.

## 13. Что не входит в текущую версию

- backend и база данных;
- ML/CV и анализ фотографий;
- настоящий алгоритм цветового соответствия;
- административная панель;
- парсинг магазинов;
- реальные цены и остатки;
- Telegram-авторизация пользователя;
- отправка уведомлений ботом;
- платежи;
- реферальная и партнёрская аналитика;
- публичная публикация пользовательских подборок.

Архитектура должна позволять добавить эти возможности позднее, но в текущем прототипе для них не нужно создавать фиктивный сервер.

## 14. Критерии готовности прототипа

Прототип можно считать готовым, если:

1. Все основные экраны доступны и связаны переходами.
2. Пользователь может пройти весь путь от главной до выбора магазина.
3. Поиск, выбор продукта, оттенка и предпочтений работают на mock-данных.
4. Рекомендации воспроизводимы и не выглядят случайными.
5. Сохранённые продукты и ответы восстанавливаются после обновления страницы.
6. Сценарий «нет данных» работает отдельно от успешной рекомендации.
7. Приложение открывается как обычный сайт и как Telegram Mini App.
8. На мобильном экране нет горизонтального скролла и обрезанных кнопок.
9. Визуальный стиль соответствует бело-серому glass-направлению и использует единый гротеск.
10. В интерфейсе явно указано, что товары, цены и результаты являются демонстрационными.

## 15. Порядок реализации

1. Создать оболочку приложения, маршруты и дизайн-токены.
2. Подготовить mock-каталог и демонстрационные соответствия.
3. Реализовать мастер подбора и сохранение состояния.
4. Реализовать результаты, карточку продукта и магазины.
5. Добавить «Мои тона», сохранённое, обратную связь и отсутствие данных.
6. Подключить безопасную оболочку Telegram Web App SDK.
7. Добавить анимации и проверить мобильную адаптивность.
8. Провести полный ручной прогон основного и альтернативных сценариев.
